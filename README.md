## 실행 방법

```bash
python main.py
```

실행 후 아래 메뉴가 표시되며, 번호를 입력해 모드를 선택합니다:

```
=== Mini NPU Simulator ===

[모드 선택]
1. 사용자 입력 (3x3)
2. data.json 분석
선택:
```

- **모드 1 (`1` 입력)**: 3×3 필터 A, 필터 B, 패턴을 직접 콘솔에 한 줄씩(공백 구분) 입력합니다.
- **모드 2 (`2` 입력)**: 프로그램과 **같은 디렉토리에 있는 `data.json`** 을 자동으로 로드하여 일괄 분석을 실행합니다.

### 모드 1 — 사용자 직접 입력 흐름

```
필터 A (3줄 입력, 공백 구분)
> 0 1 0
> 1 1 1
> 0 1 0

필터 B (3줄 입력, 공백 구분)
> 1 0 1
> 0 1 0
> 1 0 1

패턴 (3줄 입력, 공백 구분)
> 0 1 0
> 1 1 1
> 0 1 0
```

입력 오류(개수 불일치, 숫자 아닌 값)가 발생하면 안내 문구와 함께 재입력을 유도합니다.

### data.json 구조

```json
{
  "filters": {
    "size_5":  { "cross": [[...]], "x": [[...]] },
    "size_13": { "cross": [[...]], "x": [[...]] },
    "size_25": { "cross": [[...]], "x": [[...]] }
  },
  "patterns": {
    "size_5_1":  { "input": [[...]], "expected": "x" },
    "size_5_2":  { "input": [[...]], "expected": "+" }
  }
}
```

- `filters` 키: `size_{N}` (N = 5, 13, 25)
- 각 필터 내부 키: `"cross"` 또는 `"x"` (라벨 정규화로 `Cross`/`X`로 표준화됨)
- `patterns` 키: `size_{N}_{idx}` 형식. 키에서 N을 추출해 해당 크기의 필터를 자동 선택
- `expected` 값: `"+"` (Cross) 또는 `"x"` (X)

### MAC 연산 전체 흐름

MAC 연산의 코드 구조는 다음과 같은 단계를 거칩니다:

```
입력(2D 배열) → 위치별 곱셈(pattern[i][j] × filter[i][j]) → 누적 합산(total += 곱) → 점수 반환(float)
```

구체적으로 `core.py`의 `mac_operation` 함수에서:

1. **입력 수신**: 패턴과 필터를 각각 n×n 2차원 리스트로 받는다
2. **크기 결정**: `n = len(pattern)`으로 행렬 크기를 동적으로 결정한다
3. **위치별 곱셈**: 이중 반복문(`i`, `j`)으로 같은 위치의 원소를 곱한다 (`pattern[i][j] * filter_matrix[i][j]`)
4. **누적 합산**: 각 곱의 결과를 `total` 변수에 누적한다
5. **점수 반환**: 최종 누적값을 float로 반환한다

```python
def mac_operation(pattern, filter_matrix):
    n = len(pattern)
    total = 0.0
    for i in range(n):
        for j in range(n):
            total += pattern[i][j] * filter_matrix[i][j]
    return total
```

이 함수는 크기에 의존하지 않으므로 3×3부터 25×25까지 동일한 로직으로 처리됩니다.

### 패턴 키에서 크기 N 추출 및 필터 매칭 로직

모드 2에서 `data.json`의 패턴을 처리할 때, 각 패턴이 어떤 크기의 필터와 비교되어야 하는지를 **패턴 키 자체에서 추출**합니다.

**설계 방식:**

1. **키 파싱**: `extract_size_from_key("size_5_1")` → 키를 `_`로 분리 → 두 번째 요소(`parts[1]`)를 정수로 변환 → `N = 5`
2. **필터 선택**: 추출한 `N`을 기반으로 `filters[N]` 딕셔너리에서 Cross/X 필터를 가져옴
3. **크기 검증**: MAC 연산 전에 `validate_matrix(pattern, N)`으로 실제 입력 크기와 N이 일치하는지 검증

```python
def extract_size_from_key(key):
    parts = key.split('_')
    return int(parts[1])  # "size_5_1" → 5
```

이 설계의 장점은 새로운 크기(예: 50×50)가 추가되더라도 코드 수정 없이 `data.json`에 `size_50` 필터와 `size_50_{idx}` 패턴만 추가하면 자동으로 처리된다는 것입니다.

### 라벨 정규화 — 별도 함수 분리 이유와 장점

`normalize_label` 함수를 `utils.py`에 별도로 분리한 이유:

1. **단일 책임 원칙(SRP)**: 라벨 변환 로직이 한 곳에 집중되어, 정규화 규칙 변경 시 이 함수만 수정하면 됨
2. **재사용성**: 필터 키 정규화(`modes.py` 필터 로드)와 expected 값 정규화(`modes.py` 패턴 분석) 두 곳에서 동일 함수를 호출
3. **테스트 용이성**: 정규화 로직만 독립적으로 검증할 수 있음
4. **확장성**: 새 라벨(예: `'o'` → `'Circle'`)을 추가할 때 `LABEL_MAP`에 항목만 추가하면 되고, 호출하는 코드를 수정할 필요 없음

```python
LABEL_MAP = {'+': 'Cross', 'cross': 'Cross', 'x': 'X'}

def normalize_label(value):
    return LABEL_MAP.get(value.lower().strip(), value)
```

매핑 테이블(`LABEL_MAP`)을 `config.py`에, 변환 함수를 `utils.py`에 분리함으로써 **설정과 로직의 분리**도 달성합니다.

| 입력 값         | 표준 라벨 |
|----------------|-----------| 
| `"+"`          | `Cross`   |
| `"cross"`      | `Cross`   |
| `"x"` (소문자) | `X`       |

### 시간 측정 — I/O 배제 및 연산 구간 경계

성능 측정 시 **순수 MAC 연산 시간만** 측정하기 위해 다음과 같이 경계를 설정합니다:

```python
def measure_performance(pattern, filter_matrix, repeats=REPEAT_COUNT):
    times = []
    for _ in range(repeats):
        start = time.perf_counter()       # ← 연산 구간 시작
        mac_operation(pattern, filter_matrix)  # 순수 연산만 포함
        end = time.perf_counter()         # ← 연산 구간 끝
        times.append(end - start)
    return sum(times) / len(times)
```

**I/O 배제 전략:**

- `time.perf_counter()`를 `mac_operation()` 호출 **직전/직후**에만 찍어, 파일 읽기·콘솔 출력·입력 대기 시간을 완전히 배제
- 모드 2에서는 `data.json` 로드가 먼저 완료된 후, 이미 메모리에 올라간 패턴/필터 데이터를 대상으로 측정
- `time.perf_counter()`는 `time.time()`보다 해상도가 높아 ms 이하 측정에 적합
- 10회 반복 측정 후 평균을 취해 OS 스케줄링 등에 의한 편차를 완화

### 동점 처리 정책 (epsilon)

부동소수점 연산의 이진수 표현 한계로 발생하는 미세 오차를 처리하기 위해 **허용오차(epsilon)** 기반 비교 정책을 적용합니다.

```python
EPSILON = 1e-9

def compare_scores(score_cross, score_x, epsilon=EPSILON):
    if abs(score_cross - score_x) < epsilon:
        return 'UNDECIDED'   # 동점 → 판정 불가
    return 'Cross' if score_cross > score_x else 'X'
```

- `|Cross 점수 - X 점수| < 1e-9` → `UNDECIDED` (판정 불가)
- `UNDECIDED`인 경우 PASS/FAIL 비교 시 `FAIL (동점 규칙)`으로 처리

## 핵심 기술 원리

### MAC 점수가 높을수록 "더 유사하다"고 판단하는 이유

MAC 연산은 두 배열의 **원소별 곱(element-wise product)의 합**입니다. 이것은 수학적으로 두 벡터의 **내적(dot product)** 과 동일합니다.

- 패턴과 필터의 같은 위치에 **모두 1이 있으면** 곱이 1이 되어 합에 기여합니다
- **한쪽이 0이면** 곱이 0이 되어 기여하지 않습니다

즉, MAC 점수 = "패턴과 필터가 동시에 활성화된 위치의 개수"입니다.  
십자가 패턴이 십자가 필터와 매칭되면 모든 활성 위치가 일치하여 최대 점수(= 활성 셀 수)가 나오고, X 필터와 매칭되면 중앙 1칸만 겹쳐 낮은 점수가 나옵니다. 이런 원리로 **점수가 높을수록 구조적으로 더 유사하다**고 판단할 수 있습니다.

### 부동소수점 오차가 발생하는 이유와 epsilon의 필요성

컴퓨터는 실수를 **IEEE 754 이진 부동소수점** 형식으로 저장합니다. 10진수로 정확히 표현되는 수(예: 0.1)도 이진수로는 무한소수가 되어 유한한 비트에 **근사값**으로 저장됩니다.

- 예: `0.1 + 0.2 = 0.30000000000000004` (≠ 0.3)
- 곱셈과 덧셈을 반복하면 이 오차가 **누적**됩니다

따라서 두 MAC 점수를 단순히 `==`로 비교하면, 수학적으로 동일한 값이라도 미세한 오차로 다르게 판정될 수 있습니다. 이를 방지하기 위해 `abs(a - b) < epsilon` 형태의 **허용오차 비교**가 필수적입니다. 본 프로젝트에서는 `epsilon = 1e-9`로 설정하여, 이 범위 이내의 차이는 동점으로 간주합니다.

### 동점 처리를 모드 1과 모드 2에서 다르게 둔 이유

| | 모드 1 (사용자 입력) | 모드 2 (JSON 분석) |
|---|---|---|
| **동점 시 출력** | `"판정 불가"` | `"UNDECIDED"` |
| **PASS/FAIL** | 해당 없음 (단일 판정) | `FAIL (동점 규칙)` |

**요구사항 관점에서의 이유:**

- **모드 1**은 사용자가 직접 임의의 필터 A/B를 넣는 탐색적 실험 모드입니다. 필터에 Cross/X 라벨이 없으므로 "A가 이김 / B가 이김 / 판정 불가"로 표시하는 것이 자연스럽습니다.
- **모드 2**는 `expected`가 정해진 자동화 테스트입니다. `UNDECIDED`는 Cross도 X도 아니므로 어떤 `expected`와도 일치할 수 없어, 요구사항에 따라 반드시 `FAIL`로 집계해야 합니다. 이를 통해 "데이터 품질 문제"(두 필터에 동일하게 반응하는 패턴)를 검출할 수 있습니다.

## 결과 리포트

### FAIL 케이스 원인 분석

총 **8개** 케이스 중 **6개 PASS, 2개 FAIL**이 발생했습니다.  
FAIL 원인은 명세(E1-3 §3)에 따라 세 카테고리로 분리 진단합니다.

#### 1. `size_13_3` — **[수치 비교 문제]** FAIL

- **현상**: 입력 패턴이 모든 셀이 `1`로 채워진 13×13 행렬입니다.
- **MAC 결과**: Cross 필터 점수 = `25.0`, X 필터 점수 = `25.0` (완전 동점)
- **판정**: `|25.0 - 25.0| = 0 < 1e-9` 이므로 epsilon 정책에 의해 `UNDECIDED`
- **원인**: 입력 데이터 자체가 두 필터 모두에 균등하게 반응하는 구조이므로 로직 결함이 아니라 **수치 비교 상황**에서 동점으로 판정 불가 처리된 것
- **결론**: epsilon 기반 동점 처리 규칙이 정상 작동한 결과이며, `expected: X`와 다르므로 `FAIL`

#### 2. `size_5_3` — **[데이터/스키마 문제]** FAIL

- **현상**: 패턴 키는 `size_5_3`(5×5 기대)이나, `input` 배열이 3×3 크기
- **감지 방법**: MAC 연산 수행 전 `validate_matrix(pattern, 5)` 검증 실행
- **결과**: 행 수 불일치(3 != 5) 감지 → 프로그램 중단 없이 해당 케이스만 `FAIL` 처리
- **원인**: 데이터 오류(잘못된 입력 크기)이며 로직이나 알고리즘 문제가 아님
- **결론**: 스키마 검증 로직이 정상 작동했으며, 프로그램 비정상 종료 없이 케이스 단위 FAIL 처리 요구사항을 충족

#### 3. [로직 문제] 발생 없음

- 정상적인 5×5, 13×13, 25×25 Cross/X 패턴 6개는 모두 예상대로 `PASS`
- 알고리즘 자체의 연산 오류나 잘못된 판정은 없었음

### 성능 분석 표 및 시간 복잡도 해석

각 크기별 MAC 연산을 **10회 반복 측정**하여 I/O를 제외한 순수 연산 시간의 평균을 측정했습니다.

| 크기 (N×N) | 연산 횟수 (N²) | 평균 시간 (ms) |
|-----------|--------------|--------------| 
| 3×3       | 9            | 0.001        |
| 5×5       | 25           | 0.002        |
| 13×13     | 169          | 0.011        |
| 25×25     | 625          | 0.039        |

#### O(N²) 시간 복잡도 근거

MAC 연산의 핵심 로직은 **이중 반복문** 구조입니다:

```python
for i in range(n):      # N번 반복
    for j in range(n):  # N번 반복
        total += pattern[i][j] * filter_matrix[i][j]
```

- 총 곱셈 연산 횟수 = **N × N = N²**
- N이 5 → 25로 5배 증가할 때, 연산 횟수는 25 → 625로 **25배(= 5²) 증가**
- 실측 시간도 0.002ms → 0.039ms로 약 **19.5배 증가** (이론적 25배에 근접)

이 관계가 O(N²) 시간 복잡도를 실증합니다.  
실제 AI 모델은 수백×수백 필터를 수천 개씩 사용하므로, N이 커질수록 연산량이 폭발적으로 증가해 NPU 같은 전용 병렬 처리 장치가 필수적입니다.

## 심층 분석

### 새로운 라벨 추가 시 확장 순서

만약 `data.json`에 새로운 라벨(예: `'o'` → Circle 패턴)이 추가된다면, 다음 순서로 확장합니다:

1. **정규화 확장**: `config.py`의 `LABEL_MAP`에 `'o': 'Circle'` 항목 추가
2. **필터 데이터 추가**: `data.json`의 `filters` → 각 `size_N`에 `"o": [[...]]` 필터 행렬 추가
3. **판정 로직 수정**: `core.py`의 `compare_scores`를 2개 필터 비교에서 3개 필터 중 최대값 선택으로 확장 (예: `max(score_cross, score_x, score_circle)`)
4. **출력 수정**: `modes.py`에서 3개 필터 점수를 모두 출력하도록 변경
5. **테스트 데이터 추가**: `data.json`의 `patterns`에 Circle 패턴 테스트 케이스 추가 (`"expected": "o"`)

`normalize_label`이 별도 함수로 분리되어 있으므로 1단계는 매핑 테이블에 한 줄만 추가하면 되고, 나머지 코드에서 호출하는 부분은 수정이 불필요합니다.

### 1000×1000 패턴 처리 시 발생하는 문제와 최적화 방안

**시간 문제:**
- 현재 O(N²) 구조에서 N=1000이면 **1,000,000회** 곱셈+덧셈이 필요
- 25×25(625회) 대비 **1,600배** 증가 → 실측 기준 약 0.039ms × 1,600 ≈ 62ms (단일 패턴)
- 패턴이 수천 개면 총 처리 시간이 수십 초에 달함

**메모리 문제:**
- 1000×1000 float 배열 1개 = 약 8MB (64비트 float × 10⁶)
- 필터 2개 + 패턴 1개 = 최소 24MB → 수백 패턴이면 GB 단위로 증가

**우선 적용할 최적화:**

1. **1차원 배열 변환** (메모리 접근 최적화): 2D 리스트를 1D 리스트로 변환하여 캐시 지역성을 높이고, 인덱스 계산 오버헤드를 줄임 (`arr[i*n + j]`)
2. **제너레이터 활용**: 전체 패턴을 메모리에 올리지 않고 `data.json`에서 한 패턴씩 스트리밍 처리
3. **NumPy 벡터화** (라이브러리 제약이 없다면): 이중 반복문을 `np.sum(pattern * filter)`로 대체 → C 레벨 최적화로 수십~수백 배 속도 향상

### CPU 직렬 처리 vs NPU 병렬 처리 — 대규모 MAC의 병목

**CPU 직렬 처리의 병목:**
- CPU는 한 클럭에 하나의 곱셈-덧셈(MAC)을 순차적으로 수행
- 1000×1000 패턴이면 **100만 번의 순차 연산**이 필요
- 각 연산마다 메모리에서 데이터를 가져오는 **메모리 대역폭**이 병목
- 캐시 미스가 발생하면 수십~수백 클럭의 지연(latency)이 추가됨

**NPU 병렬 처리의 이점:**
- NPU는 수천 개의 MAC 유닛을 내장하여 **한 클럭에 수천 번의 MAC을 동시 수행**
- 1000×1000 연산을 1000개의 MAC 유닛으로 병렬화하면 이론적으로 **1000배 속도 향상**
- 대규모 행렬 연산에 특화된 메모리 구조(on-chip SRAM, 데이터 재사용 최적화)로 메모리 병목도 완화

**이 문제(대규모 MAC)의 핵심 병목:**
- CPU에서는 **메모리 접근 지연**(memory latency)과 **순차 실행**이 주요 병목
- 반면 MAC 연산 자체는 각 원소 간 **독립적**(i,j 위치의 곱셈이 다른 위치에 의존하지 않음)이므로, 병렬화에 매우 적합한 구조
- 따라서 NPU가 이 독립적인 곱셈-합산을 동시에 처리함으로써 성능이 비약적으로 향상되며, 이것이 AI 전용 칩이 등장한 핵심 이유
